Why a Simulation Team Needs a Tracker

A simulator is a product with customers: architects asking "what if", verification engineers comparing it with RTL, management asking whether the next chip meets its targets. The work arrives as model features, validation tasks, bugs found by comparison with silicon or RTL, and requests for studies. A tracker such as Jira turns that into a queryable record: what is being done, by whom, for which release, what is blocked, and what evidence closed it.

How this deck is built

No Jira site was used. The JQL is checked against Atlassian's documentation, and there are no screenshots of the Jira interface. The worked queries and metrics run on an example issue log for a fictional simulator team, generated from a fixed seed and labelled as such, through a small evaluator for the subset of JQL used here (snippets/t08, with its tests).

Jira changes quickly, and Atlassian is renaming things: its documentation now says work item for issue and space for project, and notes that "there are no changes to existing JQL queries". This deck uses the established terms, which is what JQL still accepts.

02

The Issue Model

  • Epics group work towards an outcome ("memory model v2"). Below them, stories are user-visible capabilities, tasks are work without a user story, bugs are defects. Sub-tasks split any of them. Children point at their epic through the parent field, which replaced the older "Epic Link" field in Jira Cloud.
  • Fields make it searchable: status, assignee, priority, fix version (the release that will contain the change), sprint, component (part of the system), labels (cross-cutting tags such as validation or regression).
  • History records every change of every field, with who and when. That is what makes flow metrics and the WAS and CHANGED operators possible.
  • Links join items ("blocks", "relates to"), and are how requirements and tests can be traced (slide 08).
03

Workflows, Transitions and Status Categories

  • A workflow is a state machine: statuses and the transitions allowed between them. Transitions can have conditions (only the assignee), validators (a field must be set) and post-functions (set the resolution).
  • Every status belongs to one of three status categories: To Do, In Progress, Done. Queries and boards that use statusCategory keep working when a team renames or adds statuses.
  • Resolution is a separate field (Done, Won't Do, Duplicate...). resolution IS EMPTY is the conventional test for "still open". Atlassian notes that service team-managed spaces have no resolution field, and recommends statusCategory = Done there.
  • For a simulation team, a status such as Validated (checked against a reference: RTL, silicon or a trusted model) between In Review and Done makes the evidence requirement part of the workflow rather than a habit.

Versions, Sprints and Kanban

Scrum (sprints)Kanban
CadenceFixed time boxes (often two weeks), planned at the start, reviewed at the endContinuous flow; items are pulled when capacity frees up
LimitsWhat is committed to the sprintExplicit work-in-progress (WIP) limits per column
Main chartsBurndown or burn-up, velocityCumulative flow diagram, cycle time
SuitsPlanned feature work: a new model component per releaseInterrupt-driven work: studies, bug reports, validation requests
  • Versions name releases of the simulator (1.5, 1.6). An item's fix version says which release will contain it. That turns "is 1.6 ready?" into a query (slide 06, query 3) and lets release notes be generated from the tracker.
  • Boards in company-managed projects are views over a saved JQL filter; dashboards are gadgets over filters. Every chart a manager sees is therefore a query that can be read, reviewed and versioned.
  • Many simulation teams run both: Scrum for the roadmap, Kanban for the stream of "can you simulate X" requests. Atlassian's Kanban vs Scrum page sets out the difference.

JQL: the Query Language

A JQL query is clauses of the form field operator value, joined by AND, OR and NOT with parentheses, optionally followed by ORDER BY. Everything below is taken from Atlassian's reference pages for fields, operators, functions and keywords.

PartExamplesWatch out for
Comparison= != > >= < <= IN NOT IN!= does not return items where the field is empty: write (assignee != currentUser() OR assignee IS EMPTY)
EmptyIS EMPTY, IS NOT EMPTY (NULL is a synonym)Only for fields that support IS
Textsummary ~ "ONNX", text ~ "flaky"Matches words and simple derivatives, not substrings
Historystatus WAS "In Review", status CHANGED FROM "In Review" TO "In Progress"Only assignee, fix version, priority, reporter, resolution and status. Predicates: AFTER, BEFORE, BY, DURING, ON (and FROM, TO for CHANGED)
FunctionscurrentUser(), openSprints(), earliestUnreleasedVersion(SIM), releasedVersions(SIM), startOfWeek()Each supports particular fields and operators (openSprints() only with IN and NOT IN)
Datescreated >= "-30d", updated < "-2w", "2026/08/01"Relative dates are measured from now
OrderORDER BY priority DESC, created ASCApplies to the whole query, at the end

Precedence matters: AND binds tighter than OR, so type = Bug AND status = Done OR priority = High returns every high-priority item, bug or not. When in doubt, add parentheses. These rules are also the test cases of the deck's evaluator.

Git and Jenkins Integration

Development work links itself to the tracker when the item's key appears in it. According to Atlassian's documentation, the key must be in the branch name, in the commit message, or in a pull request's title or source branch. The item's development panel then shows its branches, commits, pull requests, builds and deployments.

Smart commitEffect
SIM-38 #comment fixed tFAW across ranksAdds a comment to SIM-38
SIM-38 #time 1d 4h checked against DRAMsim3Logs work (w, d, h, m; decimals allowed), with the rest as its comment
SIM-38 #resolve #comment validated on the nightly sweepRuns the workflow transition whose name starts with "resolve", then comments

Syntax from Process work items with smart commits.

  • Transition names are matched up to the first space, so #start is ambiguous between "Start Progress" and "Start Review"; write #start-review. A transition fails silently if it needs a field the commit cannot set. The committer's email must match a single Jira user with permission.
  • Jenkins. The Jira side installs the Jenkins for Jira app; the Jenkins side the Atlassian Jira Software Cloud plugin, whose jiraSendBuildInfo and jiraSendDeploymentInfo steps report builds and deployments for the keys found in the commits and branch names being built (Atlassian's set-up guide). Check the current versions before relying on either.
  • The value for a simulation team: each item shows the nightly regression that tested its fix, so "is SIM-38 really fixed?" has a link to an answer (deck 07).

Traceability: Requirement, Work Item, Test, Build

  • Requirements to tests belong next to the code: an ID in the spec, the same ID on the tests, a generated matrix. Deck 09 builds one for Torch_Sim_Frontend; its first run found a requirement nothing tested.
  • Work items to requirements can use links or a field holding the requirement ID. Test-management apps from the Atlassian Marketplace model tests and runs as Jira items, if a team wants all of it in the tracker.
  • Builds to work items come from the integration on slide 07: the build that ran a requirement's tests is one click from the item.
  • The aim is a chain an auditor (or a customer) can follow from "the simulator shall..." to the run that shows it does.

The Metrics a Simulation Team Should Report

AreaMetricFromWhy it matters
FlowCycle time (50th and 85th percentile), throughput, WIP, ageing itemsWorkflow historyPredictability: "when will my study be done?"
AccuracyError against references: RTL cycle counts, silicon, trusted modelsValidation suite in CIThe simulator's reason to exist (InfSim 06)
CoverageRequirements verified; operators and workloads supportedTraceability matrix; operator coverage (deck 10)What the answers can be trusted for
QualityOpen bugs per release, escaped defects, regressions, flaky testsJQL (queries 3, 7, 10); CIRelease readiness
PerformanceSimulated events per second, wall time of the standard sweepThe CI performance gate (deck 07)Users wait for it; slow simulators get bypassed
  • Report distributions, not averages. A median cycle time of 10 days with an 85th percentile of 14 says something an average cannot.
  • Prefer metrics a tool computes from records (history, CI, the matrix) over ones people type in.
  • Goodhart's law applies: a measure that becomes a target stops measuring. Story points and velocity in particular are planning aids, not productivity measures.

Showing Progress to Sign-Off

Sign-off on a simulator release, or on a simulation study that feeds a chip decision, is a judgement made from evidence. The tracker's job is to make the evidence complete and easy to check:

Question at sign-offEvidence
Is everything planned for 1.6 done?fixVersion = 1.6 AND statusCategory != Done is empty, or each remaining item is explicitly deferred
Are the requirements verified?The traceability matrix from the release build: no gaps (deck 09)
Does the simulator still agree with its references?The validation suite's errors, against the agreed tolerances, from CI
Is it as fast as before?The performance gate's report (deck 07)
What is known to be wrong?Open bugs against the release (query 3), each with a stated impact
  • Burn-up beats burndown when scope changes: it shows the scope line moving, rather than hiding new work in a flattening line.
  • A definition of done written into the workflow (the Validated status of slide 03) makes "done" mean the same thing on every item.
  • Saved filters and dashboards turn this table into a page that is always current, built from queries anyone can read.

What to Take Away

  • The issue model is the data model: types, a workflow with status categories, fix versions, and a full history.
  • JQL makes every board, chart and report a query. Learn the traps: != skips empty fields, AND binds tighter than OR, and WAS/CHANGED only work on six fields.
  • Keys in branches and commits link code, builds and deployments to the work. Smart commits can comment, log time and transition.
  • Report flow, accuracy, coverage, quality and performance, as distributions, computed by tools.
  • Little's law checks a board: if WIP is well above throughput × cycle time, look for ageing items.
